# Проверка чертежа

[English version](checking.md)

```bash
factorio-forge check <строка чертежа или файл>
factorio-forge render <чертёж> --check -o layout.html
```

Первое печатает, что выглядит неправильно. Второе рисует чертёж с отмеченными
находками — потому что проверка может сказать **что**, а где именно, может
показать только картинка.

## Зачем это нужно

Собственные чертежи игрока — лучший источник его стиля: сетка, на которой он
строит, тир лент, длина поездов. Но не источник правильности. В настоящем
чертеже может быть случайно повёрнутая лента, так и не проложенный провод,
фильтр на манипуляторе, у которого фильтрация выключена.

Учиться по такому чертежу стилю — смысл всего проекта. Учиться его ошибкам — нет.
Значит, прежде всего нужен способ отличить одно от другого.

## Три разные вещи и разное обращение с ними

| | Что это | Что происходит |
| --- | --- | --- |
| **Стиль** | шаг сетки, тир лент, тип столбов, длина поездов | копируется, чертёж здесь главный |
| **Дефект** | лента не туда, забытый провод, простаивающий манипулятор | сообщается, никогда не перенимается как стиль |
| **Неэффективность** | несбалансированные соотношения, лишнее место | не трогается |

Третья строка намеренна. Максимальная оптимизация нужна не всем: кто-то строит
ради вида, кто-то оставляет запас, кому-то просто всё равно. Подозрения в
неэффективности здесь не сообщаются, а соотношения производства не проверяются
вовсе, пока об этом не попросят.

## Ничего не изменяется

Каждая проверка **сообщает**. Ни одна не правит. Граница между ошибкой и
намеренной странностью обычно проходит не там, где её может провести инструмент,
а инструмент, молча «чинящий» чужую компоновку, хуже того, который показывает и
спрашивает.

## Три уровня, потому что ложная тревога смертельна

Проверка, срабатывающая на обычных чертежах, приучает читателя пролистывать
вывод — и тогда настоящие находки тоже остаются непрочитанными. Поэтому находки
градуированы:

- **problem** — почти наверняка ошибка. Подземка без второго конца, манипулятор
  с пустыми клетками с обеих сторон, фильтры при выключенной фильтрации,
  комбинатор без единого провода, две ленты лоб в лоб.
- **worth a look** — есть честные причины сделать так намеренно. Машина вне
  радиуса всех столбов, столб вне досягаемости остальных, ассемблер без рецепта,
  пустой константный комбинатор.
- **note** — контекст, а не претензия. Ассемблер без рецепта в
  **параметризованном** чертеже — это заметка, потому что в этом и состоит смысл
  параметризации.

В наборе тестов проверок на то, что сообщать **не** нужно, столько же, сколько на
то, что нужно.

## Что видит читатель: ошибки и факты

Три уровня выше — то, как думают проверки. В отчёте два уровня:

- **ошибка** — чертёж не встанет или не заработает: столкновение, вход, который
  ничто не питает, не тот предмет на полосе, не хватает подачи, сеть столбов
  разорвана.
- **факты** — что это за постройка: темпы, загрузка лент («полоса кабеля
  загружена на 80 %»; одна полоса сравнивается с ёмкостью одной полосы, из ленты и подземки берётся более медленная), какие предметы по каким полосам идут, число объектов и
  машин, что было принято по умолчанию. У факта нет вердикта: что он значит,
  решает читатель.

Промежуточного уровня нет. Сомнительная находка (*worth a look*) — это ошибка, и
её текст говорит, что проверить; если неясно, ломает ли что-то постройку, оно
выводится как ошибка. Градация остаётся внутри (`Finding` и `Severity` не
менялись); `report.py` лишь сводит её к двум уровням.

`build` и `check` сначала печатают одну строку — `N errors` или `no errors`, —
затем ошибки, затем факты. `check` показывает факты из находок только с
`--all`. В `report.json` есть массивы `errors` и `facts` (в записи: `text`,
`kind` и, где применимо, `code`, `detail`, `position` и собственная оценка
проверки `severity`). Собственные предупреждения сборки (файл запроса не читается, часть плана пропущена) — тоже ошибки, `kind: "warning"`: это сбои, а не допущения. Старые поля `findings` и `warnings` пока пишутся для
совместимости и **устарели**: читайте `errors` и `facts`.

Каждый код находки и как он показывается («error; note: fact» — ошибка, если
проверка оценила его как problem или worth a look, и факт, если как note):

| Код | Показывается как | Что значит |
| --- | --- | --- |
| `overlap` | error | два объекта, которым нельзя стоять на одних клетках |
| `unknown-prototypes` | error | типы объектов, которых нет в используемых данных игры |
| `belts-head-on` | error | две ленты смотрят друг на друга |
| `underground-unpaired` | error; note: fact | подземка без второго конца |
| `inserter-idle` | error | манипулятор без источника или приёмника |
| `inserter-loop` | error | манипулятор, возвращающий предметы в ту же машину |
| `inserter-backwards` | error; note: fact | манипулятор, похоже, повёрнут не туда |
| `filters-ignored` | error | фильтры при выключенной фильтрации |
| `condition-without-wire` | error | условие схемы без провода |
| `combinator-unwired` | error; note: fact | комбинатор без проводов |
| `constant-empty` | error | константный комбинатор без сигналов |
| `machine-no-recipe` | error; note: fact | машина без рецепта (заметка в параметризованном чертеже) |
| `unpowered` | error | объект вне радиуса любого столба |
| `pole-isolated` | error | столб вне досягаемости других столбов |
| `power-split` | error | столбы образуют несколько отдельных сетей |
| `signal-without-rail` | error; note: fact | сигнал не рядом с рельсом |
| `fluid-box-unconnected` | error | жидкостное соединение, ведущее в пустоту |
| `fluids-mixed` | error | две разные жидкости в одной сети труб |
| `lanes-not-taken` | error | предмет приходит на полосу, с которой его никто не берёт |
| `lanes-mixed` | error | два предмета делят одну полосу |
| `lanes-nothing` | error; note: fact | туда, где блок ждёт предмет, ничего не приходит |
| `lanes-missing` | error | нужный блоку предмет не приходит |
| `lanes-wrong` | error | нужные предметы, но не на тех полосах |
| `lanes-wrong-item` | error | приходит не тот предмет, что нужен блоку |
| `lanes-starved` | error | блоку не хватает входа |
| `lanes-rate` | error; note: fact | заявленной подачи меньше, чем просит заказ (заметка: меньше полной нагрузки) |
| `lanes-unknown` | error; note: fact | что входит в точку, не объявлено, поэтому полосу проверить нельзя |
| `route-lanes-disagree` | error | полосы маршрута и прослеженные полосы расходятся |
| `lanes-overflow` | fact | полоса заполнена, остаток уходит другим путём через разделитель |
| `lanes-swapped` | fact | полосы пришли в обратном порядке, блок берёт с обеих |
| `lanes-unchecked` | fact | полосы после точки не прослеживаются, с причиной |
| `route-failed` | error | соединение, которое не удалось проложить |
| `route-belt-slow` | error | лента или полоса несёт меньше, чем нужно маршруту |
| `route-short-supply` | error | начало подаёт меньше, чем хочет конец |
| `route-split-cascade` | fact | несколько приёмников за цепочкой разделителей делят поток неровно |
| `route-no-underground` | fact | у ленты нет подземки; маршрут идёт по поверхности |
| `route-underground-speed` | fact | подземка и лента разной скорости |
| `route-tiles-unchecked` | fact | плитки карты инструменту неизвестны (вода, лава) |
| `block-short` | error | блок делает меньше, чем нужно заказу |

Новая проверка не выйдет без строки здесь: тест читает исходники в поисках кодов
находок и падает на тех, которых нет в `report.RULES`.

## Края

Большинство чертежей — фрагменты, рассчитанные на стыковку с чем-то ещё. Лента,
уходящая за край, — норма; как и машина без питания в куске, где энергетики нет,
и манипулятор у границы, чей сосед находится в соседнем чертеже.

Поэтому каждая проверка, способная иначе срабатывать на половине всех чертежей,
знает про края: всё, что тянется за границу, считается встречающим то, что
снаружи. А там, где полное молчание сделало бы проверку бесполезной — рельсовый
сигнал по своей природе стоит у края чертежа, — находка не подавляется, а
понижается до **worth a look**.

## Что проверяется

Одна идиома выглядит в точности как ошибка и ею не является. Чертежу, который
собираются параметризовать, нужна свободная переменная — а делается она
постоянным комбинатором со значением, которого нигде больше нет, и без единого
провода. Такой комбинатор отмечается, а не осуждается; пустой по-прежнему
сообщается своей собственной проверкой.

Перекрытие сообщается только тогда, когда его отвергла бы сама игра: маски
столкновений должны делить слой, **и** настоящие коробки столкновений должны
пересекаться. Общая клетка не значит ни того, ни другого — сигнал занимает пятую
часть клетки, а диагональный рельс это наклонная фигура внутри квадрата из
четырёх, — и подсчёт по клеткам дал тридцать одно «столкновение» на чертеже,
снятом с работающей карты, где их заведомо нет. Рельсы исключены из проверки
вовсе: их настоящие формы криволинейны, доступная здесь геометрия приближает
каждую прямоугольником, и на стыке эти прямоугольники пересекаются, а рельсы —
нет.

Связность и геометрия: подземные ленты и трубы без второго конца, манипуляторы,
не достающие ни до чего или перекладывающие из контейнера в него же, ленты лоб в
лоб, сущности на одной клетке, рельсовые сигналы не у рельса.

### Манипуляторы, повёрнутые не туда

`direction` манипулятора называет сторону, с которой он *берёт*: направление на
север берёт с клетки севернее и кладёт на юг. Ряд, нарисованный на глаз,
легко зеркалится, а манипулятор между двумя объектами для проверки «простаивает
или крутит по кругу» выглядит нормально при любом повороте. Поэтому
`inserter-backwards` спрашивает каждую сторону, что она несёт: берёт рецепты
машин по обе стороны и то, что известно трассировщику полос о лентах (клетки
взятия и сброса берутся из досягаемости манипулятора, так что длиннорукий
оценивается так же):

- **проблема** — продукт машины кладётся на ленту, несущую один из её же
  ингредиентов, и с этой ленты в машину никто не берёт (входной манипулятор
  развёрнут наоборот); две машины, соединённые манипулятором, у которых продукт первой
  не ингредиент второй; предмет берётся с ленты в машину, которой он не нужен.
- **проблема** (при сборке плана, где источники заявлены) — машина, которой никто
  не несёт ингредиент, и манипулятор, берущий с ленты, на которую ничего не
  кладут.
- **посмотреть** — машина, продукт которой никто не забирает, а все её
  манипуляторы только несут ей что-то с лент (выходной манипулятор развёрнут
  наоборот); зеркальный случай: все манипуляторы машины только забирают из неё,
  и ни один ничего не несёт (входной развёрнут наоборот), когда источники не
  заявлены; то же при сборке плана, если машина у края чертежа, где подача может
  быть за его пределами.

Лента, служащая и входом, и выходом одной машины, нормальна, даже если выходной
манипулятор стоит выше по ленте, чем входной. Если развёрнуты оба манипулятора,
сообщается только о входной стороне.

Ничего не говорится там, где ответ зависит от того, чего на картинке нет: лента
с неизвестным содержимым, машина без рецепта, сундук, топливная машина, которой
могут подавать топливо, машина рядом с погрузчиком. Лента, начало которой никто
не заявил, пустой не считается. Один чертёж оценивается лишь настолько, насколько
сам делает свои предметы; при сборке плана содержимое лентам дают заявленные
`sources`.

Энергия: машины вне радиуса всех столбов, столбы, оторванные от остальной сети.

Настройки, которые молча ничего не делают: фильтры на сущности с выключенной
фильтрацией, условие схемы или логистики на сущности, до которой не доходит
провод, комбинатор вообще без проводов, константный комбинатор без сигналов,
ассемблер без рецепта.

## Полосы (при сборке)

`factorio-forge build` проходит по каждой полосе каждой ленты чертежа —
лентам блоков, поставленным руками и проложенным трассировщиком (`lanes.py`) —
и сверяет, что полоса везёт, с тем, что с неё берут. Левая и правая — по ходу
ленты. В `factorio-forge check` пока не запускается.

**Как лента принимает то, что в неё толкают** (Factorio 2.0):

| Принимает | сзади | навстречу | сбоку |
|---|---|---|---|
| лента | продолжает прямо | тупик | см. ниже |
| вход подземки | продолжает прямо | в козырёк: тупик | правило козырька |
| выход подземки | в козырёк: тупик | тупик | не отслеживается |
| половина сплиттера | в эту половину | тупик | тупик |
| погрузчик, связанная лента | выход: берёт всё | | |
| что угодно ещё (столб, станок, сундук, манипулятор ...) | тупик | тупик | тупик |
| ничего | открытый конец, кроме хвоста входной линии блока | | |

- Лента, которую кормят сзади или с обеих сторон, — прямая: каждая боковая
  подача подгружает обе свои полосы на ближнюю. Если её кормит только одна
  подача сбоку — это поворот, полосы сохраняются, чем бы ни кормили: обычной лентой,
  выходом подземки или выходом сплиттера (проверено в игре).
- **Правило козырька**: в бок входа подземки проходит только полоса подачи со
  стороны открытой части входа и ложится на ближнюю полосу; другая полоса —
  тупик (`lanes.hood_passes`, проверено в игре).
- Подземная пара сохраняет полосы. Сплиттер отправляет левую полосу каждого
  входа на левые полосы обоих выходов, правую — на правые; фильтр и приоритет
  не моделируются (заметка).
- Предметы появляются из объявленного начала (точка маршрута или `inputs`
  плана), из выброса манипулятора (что делает станок, из которого он берёт, —
  через его фильтр; что он снимает с другой ленты; иначе неизвестно), из
  выброса бура (неизвестно), в голове ленты на краю чертежа или за
  погрузчиком (неизвестно) и в голове ленты, поставленной руками, где угодно,
  если её не назвали в `inputs` (неизвестно; порт, куда это доходит, получает
  `lanes-unknown`). Голова ленты блока или маршрута в других местах не везёт
  ничего. С
  ленты манипулятор берёт ингредиенты рецепта станка, который он кормит, или
  что угодно — для сундука, лаборатории или печи без рецепта.

**Открытые и закрытые концы.** Лента, смотрящая в пустую клетку, — открытый
конец: в мире она может идти дальше, как везде в проверке. Тупики закрыты
(лента, смотрящая в столб, станок или сундук, — тоже тупик), и
закрыт хвост входной линии блока: ей и положено там кончаться. В закрытом
конце каждый предмет полосы должен быть кем-то взят по пути, иначе он
забивает полосу.

**Правила.**

- R1, в каждом закрытом конце: предмет, который выше по ленте никто не
  берёт, — *застрявший*. `lanes-not-taken` (проблема), если он делит полосу с
  нужным предметом — полоса забьётся, и нужный перестанет приходить;
  (подозрение), если он на полосе один. Вместо этого `lanes-overflow`
  (заметка), если сплиттер по пути отправит его весь на другой выход, где его
  берут. `lanes-mixed` (подозрение), если два нужных предмета делят полосу:
  если они не приходят в той пропорции, в какой тратятся, один запрёт другой.
- R2, в каждом входном порту и в каждой проложенной точке-назначении с
  предметами: `lanes-missing` (проблема), если ингредиент не приходит
  никогда; `lanes-wrong-item` (проблема) называет каждую полосу, которая везёт
  ненужный блоку предмет, пока ингредиента не хватает; `lanes-nothing`, если
  к порту не приходит ничего (проблема, если там кончается соединение, иначе
  подозрение); `lanes-unknown` (подозрение на входном порту блока, заметка
  в точке), если этого не сказать, потому что заходит что-то необъявленное —
  объявить его в `sources` плана; `lanes-rate`, если объявленные источники
  дают меньше, чем нужно порту, сравниваются суммы (проблема, когда в плане
  есть заказ, заметка при полной загрузке); `lanes-swapped` (заметка), если два
  ингредиента блока пришли на полосы друг друга — его манипуляторы берут с
  обеих, так что он работает как есть. Точка упорядочена: `lanes-wrong`
  (проблема), если её полосы не совпадают, с пометкой, если они просто
  перепутаны. `route-lanes-disagree` (проблема), если представление
  трассировщика о полосах маршрута расходится со следом.
- R3: `lanes-starved` (проблема), если станки, чьи манипуляторы берут только
  с лент с известным содержимым, никогда не получают ингредиент; не
  повторяется, если порт уже сообщил, что его нет.
- `lanes-unchecked` (заметка) — для каждого места, за которым полосы не
  отслеживаются.

**Тишина.** Неизвестное содержимое само по себе замечаний не даёт. Входной
порт, куда не приходит ничего известного и куда не ведёт маршрут, — не
подключённый кусок, его не судят; станок, чьи ленты не несут ничего
известного, не называют голодающим.

## Ничего об объектах не захардкожено

Моды меняют эти числа, нередко в разы, поэтому каждое из них читается из игровых
данных профиля в момент проверки. Под Krastorio 2 скоростная подземка достаёт на
**двадцать** клеток там, где ваниль даёт девять, а сам мод добавляет подземки на
тридцать и сорок. Подземная труба тянется на двадцать вместо десяти. Константа в
коде была бы верна для ванили и грубо неверна для игрока.

Ленты сообщают дальность прямо, трубы прячут ту же величину в своём fluid box —
читаются оба места. Если ответа нет нигде, проверка **пропускается**, а не
выполняется на выдуманном числе: незнание — это факт, а не право предполагать.

Направление подземного хода тоже берётся из прототипа. Труба показывает открытый
конец над землёй, а ход прячет **позади** себя: в прототипе перечислены два
соединения по отдельности, видимое в направлении объекта и подземное в
противоположном. Предположение, что ход идёт по направлению взгляда, дало
восемнадцать «непарных» труб в одном настоящем ситиблоке — и у каждой пара
нашлась в другую сторону.

Досягаемость манипулятора берётся из `pickup_position` и `drop_position` самого
чертежа, если он их несёт, и из сообщённых объектом в противном случае. Чертёж,
который их указывает, описывает то, что записала игра, уже ориентированным;
моды, позволяющие манипулятору тянуться вбок или по диагонали, выражают себя
целиком через эти числа. Ни то, ни другое не выводится из направления. Это избавляет от рассуждений о том, куда
указывает `direction` (указывает он противоположно очевидному — на ту сторону,
**откуда** берёт), но важнее другое: мод может вообще изменить связь между
направлением и досягаемостью. Bob's Inserters позволяет манипуляторам брать под
девяносто градусов. Чтение сообщённых позиций сохраняет правильность само собой,
формула — нет.

## Отчёт называет данные, на которых построен

Один и тот же чертёж закономерно даёт разные ответы при разных сборках. Разрыв в
пятнадцать клеток между скоростными подземками нормален под Krastorio 2 и сломан
под ванилью, и оба вердикта верны. Поэтому каждый отчёт называет профиль, против
которого получен.

Если в чертеже есть сущности, о которых загруженные данные никогда не слышали, об
этом говорится **первым делом и как о проблеме**: почти всегда это значит, что
активен не тот профиль, — а от этих данных зависят все остальные находки, так что
доверять отчёту нельзя, пока это не исправлено:

```
2 entity type(s) are missing from the game data in use
    Not found: kr-advanced-underground-belt, kr-superior-inserter.
    The data being read is space-ageeeeeeeee. Everything else in this report
    depends on that data, so activate the profile this blueprint belongs to
    and check again.
```

## Замер того, что делает постройка

Все проверки выше читают чертёж. Последняя - запустить его: `/forge-measure` из
мода-спутника строит чертёж на своей пустой поверхности (с параметрами планеты,
для которой сделан план), подаёт сырьё в каждый объявленный источник,
опустошает каждый конец выходной ленты, гоняет разгон и замеряемый отрезок и
пишет `measure.json`. Это проверка того, что чтением не найти: соотношение,
из-за которого станок голодает, выход, который забивается, подача, которую лента
не вывозит.

```
factorio-forge measure spec plan.json --surface vulcanus -o spec.json
tools/headless-run.ps1 -Save my-save.zip -Out out -Measure spec.json     (репозиторий мода-спутника)
factorio-forge measure result out/measure.json --spec spec.json
```

`measure spec` собирает план и пишет запрос: чертёж, источники, выходы и `targets`
плана. Источник - каждая запись `sources` плана и каждое соединение, у которого
`from` - точка с предметами и темпом (`{"at", "direction", "items", "rate"}`):
это подача, начинающаяся там, она пишется как `connection <id> start`. Выход -
каждый выходной порт-лента, из которого никто не ведёт маршрут, и каждый
маршрут, который правда кончается в свободной точке. Маршрут, который вливается
`onto` в ленту, выходом не считается: лента идёт дальше, и опустошать её там
значит голодить то, что она кормит. Пустая полоса предметом не пишется никогда, а
соединение, у которого полосы не по одному предмету, пропускается с заметкой.
Источником может быть и `{"block", "port", "fluid", "rate"}` (единиц в секунду)
на входном порту-трубе: в замере на клетке порта стоит бесконечная труба.
Отказ, если в порт кончается соединение или его уже кормит другой источник;
`build` проверяет его, как ленточные источники. `chain` и `base --drafts`
записывают такие источники для жидкостей, которых не делает ни одна ступень цепочки.
`--output-end X,Y[,ITEM[,DIR]]` добавляет конец выхода для плана с лентами
вручную, `--fluid X,Y,FLUID[,RATE]` - источник жидкости на клетке с вашей трубой, `--target ITEM=RATE`
заменяет цели плана; `--warmup`, `--seconds` и `--speed` задают прогон (60 с,
120 с, скорость игры 10). `rate` источника - предметов в секунду на обе полосы,
как в плане; без `rate` источник подаёт, сколько лента возьмёт.

`measure result` печатает по каждой цели заказ и замер, где замер - то, что
дошло до концов выходных лент (а без конца выхода - то, что выпустили станки),
затем как каждый вид станков провёл окно и чего ждали голодавшие:

```
targets (ordered -> measured):
  iron-gear-wheel: ordered 0.5/s, measured 0.5/s at the output belts (100%), machines made 0.5/s [ok]
machines:
  1 x assembling-machine-1 (iron-gear-wheel): working 50%, waiting input 50%
starved: 1 x assembling-machine-1 (iron-gear-wheel) waited for input 50%: iron-plate missing 50% of the time
result: every target met
```

Цель считается выполненной от 95% заказа. Станок называется голодающим, когда
четверть окна и больше ушла на ожидание ингредиента, и заблокированным, когда на
полный выход; любое время без питания сообщается. Код выхода 0, если все цели
выполнены, иначе 1. Также сообщаются построенные объекты против ожидаемых,
прототипы, от которых игра отказалась, подача, которую лента не взяла (реально
поданный темп против заявленного), и станки без рецепта (рецепт, чьи условия
поверхности на планете не выполнены, при вставке отбрасывается, как в настоящей
игре).

Недобор не всегда значит плохой план, и `measure result` под станками отличает
одно от другого. Если станок последней стадии не хватало сырья, которое за всё
окно не сделал ни один измеренный станок и не подал ни один источник, заметка
так и пишет: сырьё, которое никто не делает и не подаёт, - это пропавший
источник, а то, чьи станки не сделали ничего, голодало выше по цепочке; более
долгий прогрев не меняет ни то ни другое. Если всё сырьё дошло, а цель при этом
недобрана, но выше 0 (или её станки ждали сырьё четверть окна и больше), линия,
возможно, ещё заполняется, и заметка всегда советует запуск с прогревом минимум
вдвое длиннее. Верь цифре, когда два окна сходятся: если длинный прогон показал
то же - дело в плане, если цифра выросла - линия заполнялась. Ещё заметка
называет нижнюю границу времени заполнения: самая длинная цепочка «время рецепта
/ скорость станка» из данных игры плюс путь по лентам вдоль самой длинной цепочки
маршрутов (его `measure spec` записывает в спеку как `belt_travel_s`). Граница
считает по одной варке на стадию, без буферов станков, наполнения лент и модулей,
поэтому на деле заполнение дольше (прогрева в 240 с не хватило линии с границей в
72 с); это объяснение, а не проверка.

Что за числа: выпуск и расход - статистика производства силы по поверхности
замера; доставка считается в стоках. Питание - тестовый источник в один гигаватт,
поэтому питание никогда не предел; источники жидкости - бесконечные трубы, поэтому
и жидкость никогда не предел. Измеренные темпы - это темпы постройки, которой
подали ровно то, что объявлено в плане.

## Выдача чертежа: `deliver`

```bash
factorio-forge deliver plan.json [-o папка] [--save ИМЯ_ИЛИ_ПУТЬ] [--no-game-check]
```

`deliver` - это `build` с ещё одним шагом: когда в сборке нет проблем, чертёж
ставится в настоящей игре без окна на пустую площадку (`tools/headless-run.ps1
-Blueprint` мода-спутника, он запускает `/forge-verify`; около 20-30 секунд).
Модель за `check` быстрая и может ошибаться, игра - нет. Это отдельная команда, а
не флаг `build`, чтобы `build` оставался быстрым циклом правки плана, а `<имя>.txt`
содержал либо чертёж, который игра поставила, либо чертёж, записанный, когда игру
вообще нельзя было спросить (какой случай - в `game_check.status` отчёта, это же
печатается). После отказа или сорвавшегося прогона `<имя>.txt` не остаётся: старый
файл прежней сборки переименовывается в `<имя>.stale.txt`.

| Итог | Код выхода | Файлы |
| --- | --- | --- |
| игра поставила всё | 0 | `<имя>.txt`, отчёт, рисунок |
| игра поставила меньше, чем записал forge, или отказала целому виду построек | 1 | `<имя>.unverified.txt` вместо `<имя>.txt` и `<имя>.game-refused-test.py` |
| в сборке есть проблемы (игру не спрашивают) | 1 | только отчёт |
| проверка настроена, но не запускается (Factorio уже открыта, нет сейва или скрипта запуска, мод-спутник старый или нечитаемый, прогон упал или завис) | 1 | `<имя>.unverified.txt`, без заготовки |
| эта машина не может спросить игру вообще | 0 | `<имя>.txt` и строка `not checked in the game: <причина>` |

Спросить нельзя только если: не Windows, нет PowerShell, Factorio не найдена или
мод-спутник не указан. Если мод указан, ошибка (неверный путь, нет сейва, открытая
игра) - это сорванная проверка, а не тихий пропуск. Причина печатается и пишется в
отчёт как есть. `--no-game-check` пропускает проверку намеренно и говорит об этом
так же.

Заготовка теста - готовый тест для `tests/`: в ней план и ответ игры, а проверяет
она, что модель тоже находит в этом плане проблему. В заготовке есть план (и темпы,
с которыми шла выдача), она сама пропускается там, где в данных нет нужной
постройки или рецепта, и помечена как ожидаемое падение (strict), так что вставка
не краснит набор тестов. Когда модель научится правилу, тест начнёт проходить,
pytest скажет об этом, и метку `xfail` нужно убрать - случай останется
регрессионным тестом. Имена и числа приходят из игры (имена
построек выбирают моды), поэтому в комментарий и в код склейкой они не попадают:
в заготовке они только как литералы Python, записанные через `repr`, а перед
записью инструмент разбирает заготовку обратно и сверяет.

Настройка. Укажите `deliver` папку репозитория мода-спутника переменной среды
`FACTORIO_FORGE_COMPANION` (или ключом `companion` в `config.json` в домашней
папке forge, или `--companion`). Папка копируется во временную, и
архив мода собирает там её собственный `tools/build.ps1`: список файлов -
мода-спутника, в репозиторий ничего не пишется. Если переменная указывает на готовый `.zip`,
скрипт запуска задайте через `FACTORIO_FORGE_RUNNER` (ключ `runner`). Сейв - тот,
из которого сделан активный профиль, ищется в папке сохранений игры; `--save`
принимает имя или путь. Запуск идёт на копии во временной папке, а после прогона проверяет,
что настоящие сейвы, список модов и настройки модов не изменились; если изменились,
он завершается с кодом 1, и `deliver` чертёж не отдаёт. Мод-спутник должен быть
0.7.1 или новее (более старый срывает проверку сразу). Если прогон завис,
`deliver` завершает оболочку и всё, что она запустила (`taskkill /T`); временная
папка запуска при этом остаётся в temp.

Чего проверка не говорит: площадка пустая, поэтому ответ - «ставится ли чертёж сам
по себе», а не «влезет ли он в базу игрока» (для этого нужна постановка на реальные
координаты в копии сейва). Если постройки накладываются, игра может их слить и не
назвать ни одной; счёт «поставлено из ожидаемого» чертёж всё равно задержит, но
имён в вердикте не будет.

## Чего ещё нет

Логика схем в осмысленном виде пока не проверяется. Комбинатор без проводов
ловится, но делает ли схема то, ради чего построена, — вопрос для тактового
симулятора, который идёт следующим.
